## 1. エグゼクティブサマリ

本プロジェクトは、気象庁・国土交通省・環境省・Open-Meteo の公開データを統合し、
土木現場の作業判断（コンクリート打設・クレーン・河川内作業・土工・舗装・熱中症・海上作業）を
「レベル0〜3」と根拠付き理由で支援する Web アプリです。

2026-08-12 時点で、認証（JWT+RBAC＋現場単位権限）、監査ログの原子性、ログイン試行制限、
トークン失効、本番起動ガード、バックアップ・復元ドリル、systemd 監視、CI 5ジョブ、
backend 463 件 / frontend 80 件のテストが整備された「**条件付き利用可**」の段階にあります。

18 基準の改善前スコアは **平均 64.8 / 100**、改善後 **65.7 / 100**、競合代替率は
**50.5% → 53.1%**（加重）と評価しました。本セッションでは以下を実装・検証しました。

- PR #139（CI ハードニング・loopback/技術スタック文書同期・env 案内）: CI 5ジョブ green
- 本番新規DBへのデモ現場・判断履歴の自動投入を抑止（`SEED_DEMO_DATA` 安全側既定）
- 現場詳細の公式リンクを `site_links` API から表示（Issue #85 対応）
- Open-Meteo 帰属表示（CC BY 4.0）を UI へ追加（利用条件確認書 #114 のギャップ解消）
- 並行 pytest のテストDB競合をロックで直列化（ローカル再現性）
- 本評価書・残課題・ロードマップの整備

**総合判定: 条件付き利用可**

「本番利用可」とするためには、下記 P0 群（#114/#115/#116/#119）と河川公式データ接続、
モバイル/PWA、通知実配信、AI 機能の費用対効果検証が必要です。

## 5. 強み（15件以上）

1. 判断支援思想が徹底: 「作業可能」と断定せずL0-3＋根拠・データ元・鮮度を明示（README・判定エンジン）
2. 公式データ優先: 気象庁警報を外部予報より優先、河川・WBGT も公式導線（assessment.py / jma_warnings.py）
3. 欠測・遅延を安全側へ: 主要データ欠測→確認不能(3)、STALE縮退を理由として明示（decision_engine.py）
4. 現場単位RBAC＋役割境界: admin/tech_manager/site_manager/safety/viewer＋site_editor/site_decision（site_access.py、テスト済み）
5. 監査ログの原子性: ドメイン変更と監査を同一トランザクション（#63、複数テスト）
6. ログイン試行制限とトークン失効をDB永続化（login_attempts / revoked_tokens）
7. 本番起動ガード: JWT_SECRET 32B+/暗号鍵/ADMIN_PASSWORD/CORS/PG必須を起動時に強制（config.py）
8. 閾値の監査・再現: DecisionResult に thresholds_json スナップショット保存
9. ID採番の並行安全性: IdCounter + リトライ（#49）
10. 判定結果・理由・実測値の永続化とCSV出力（決定ログ・Excel対応BOM）
11. セキュリティヘッダ＋本番docs無効化＋loopback bind＋Cloudflare Tunnel限定公開
12. バックアップ自動化: 日次dump→暗号化export→復元ドリル＋鮮度/オフサイトチェック systemd 群
13. 監視スクリプト群: health/security surface/network exposure/public edge/disk/secret permission/ops status
14. CI 5ジョブ（lint/test/security/frontend/e2e/docker）が常時 green
15. テスト資産: backend 463 / frontend 80 / E2E / policy系（CDN・proxy・vendor・SRI）
16. 文書体系が充実: README/要件/設計/実装計画/運用台帳/Runbook/SLO/受入基準/データソースカタログ
17. 本番検証の実績記録: リリースノートに本番スモーク・障害対応（共有クライアント劣化）を記録
18. 秘密情報を Git へ置かない設計: .env.example はプレースホルダのみ、テストは架空接続文字列

## 10. AI の設計方針

- **AI不要の領域**: 閾値判定・警報反映・欠測表示・RBAC・監査はルールベースを維持（説明可能性と監査性を優先）
- **AIの対象**: ①判定理由の平易な文章化、②類似過去判断の検索、③社内基準・公式資料へのRAG検索、④データ異常検知
- **構成**: DeepSeek/Anthropic API＋プロンプト固定化、RAGは公式資料＋社内承認資料のみを index、モデル・プロンプト版数を監査保存
- **根拠・引用**: 出力に引用IDと信頼度（高/中/低）を必須化。引用できない出力は「参考」扱い
- **人間承認**: 判断の最終記録（execute/postpone/cancel）は人間操作のみ。AI提案の自動適用は禁止
- **権限制御**: AI機能もロール・現場単位権限を経由。出力先に含まれる現場データは権限フィルタ適用
- **プロンプトインジェクション**: 入力（現場名・コメント等）はシステムプロンプトへ混入させず、データは構造化フィールドで受け取り、出力はエスケープ。公式サイトURL等の外部入力は許可リスト
- **個人・機密保護**: 個人情報は入力項目に含めず、社外秘の施工計画書は要承認資料のみ登録。AI API へ送るのは必要最小限
- **監査**: モデル名・プロンプト版数・入力要約（秘密値は除外）・出力・利用者・時刻を監査ログへ記録
- **誤判定時の責任分界**: UIに「AIは参考。最終判断は現場責任者」を常時表示し、リリース前に受入基準（危険側誤判定0件）を適用
- **費用制御**: ユーザー/月/日ごとの利用量上限、予算アラート、ワンタッチ停止（kill switch）を管理画面へ実装
